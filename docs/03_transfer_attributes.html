Pass-through chain dissolution → direct coordinate-join match → nearest-constituent attribute resolution

Model links are dissolved across pass-through (unsnapped) node chains, then each physical link piece from 02_create_link.qmd is matched to its dissolved chain via a direct, direction-sensitive (A,B) coordinate join — no graph traversal or synthetic geometry involved. Every piece’s real geometry is retained regardless of match outcome; attributes are resolved via nearest-constituent-to-centroid distance and left blank when unmatched.

Model Links

Filtered the same way 01_node_classification.qmd filters when it computes NeighborCount/is_topo_passthrough: LN_2027 > 0 AND FT_2027 NOT IN (1, 37, 38, 39). Centroid connectors (FT=1) and non-physical HOV/Managed- Access links (FT=37,38,39) are excluded outright; everything else must additionally have at least one lane by 2027 to count as part of today’s (or 2027’s) connectivity graph — a link coded zero-lane in 2027 doesn’t yet exist as a driveable connection, even if a physical centerline sits near its geometry. This match matters beyond just filtering consistently: if this notebook’s dissolve graph could see an edge that 01 didn’t count, a node 01 classified pass-through (NeighborCount==2) could turn out to have a 3rd, LN=0 neighbor here — and dissolve_pseudonodes’s walk, trusting the NeighborCount==2 guarantee, would silently take the wrong edge through it. LN_2027/FT_2027 themselves are reported unchanged on matched output — this only affects whether a chain counts as connected, not what gets displayed.

Snapped Nodes

Stage 2 guarantees every link_pieces.gpkg boundary is already a snap point, so Stage 3 needs which nodes are snapped (split points) versus not. For the “not” side, is_topo_passthrough from nodes_classified.gpkg (NeighborCount==2, regardless of FT, lane count, or link-class/designation uniformity) is safe to silently walk through and absorb into a multi-hop chain in Part A — a node with exactly two distinct neighbors has exactly one way to continue through it, full stop, no matter what changes there on the model side. An unsnapped node that fails even that (3+ neighbors — a real junction) is not pass-through: dissolve_pseudonodes’s single-preferred-edge walk has no reliable way to know which of several real branches continues the correct chain, so treating every unsnapped node as pass-through (as an earlier version of this notebook did) silently produced wrong-branch chains at those nodes. Only 2-neighbor nodes are dissolved through; any 3+-neighbor unsnapped node is left as a hard chain boundary, and pieces touching it honestly fail to match rather than getting attributed from a guessed direction.

This is deliberately broader than is_pseudo (which additionally requires uniform FT and uniform lane count, because it also gates Stage 1 snapping eligibility — a snap target needs that stricter guarantee). Stage 3 only needs the topological guarantee: real FT-transition, lane-transition, and link-class-transition nodes have no physical vertex of their own in the UGRC/UDOT centerlines (arcpy only cuts at genuine junctions), so treating them as hard chain boundaries here — while is_pseudo correctly still sends them to snapping in 01_node_classification.qmd — was silently splitting one physical piece across a model chain boundary the physical network was never actually cut at. See _plan/freeway-endpoint-pool-diagnosis.md and the node-30208 (Antelope Island Causeway) example that first surfaced this.

FixedTransit_Rail-snapped nodes are excluded from snapped_node_ids — they attach to GTFS rail infrastructure, not road centerlines, so they were never road-piece split points in Stage 2 either (02_create_link.qmd applies the same exclusion).

3 Part A — Pass-Through Chain Dissolve

Collapse chains of model links connected through pass-through nodes — the topological pass-through set (pass_through_ids = pseudo_ids - snapped_node_ids; the subtraction is defensive, these nodes are never snapped by design — see 01_node_classification.qmd’s is_topo_passthrough). A node only qualifies if it has exactly two distinct neighbors (NeighborCount==2) — that alone is the guarantee the walk needs to be safe: at a 2-neighbor node there is exactly one way to continue the chain, so dissolve_pseudonodes’s preferred-else-first-found edge choice can’t pick wrong, regardless of whether FT, lane count, or link class (freeway/ramp/ surface designation) changes there. Only a real 3+-way junction — where topology alone can’t say which branch continues the same physical road — is not pass-through here: it’s a hard chain boundary, same as a snapped node. Pieces whose real physical boundary sits at such a junction will fail to match (endpoints_only/a_only/b_only) rather than silently being attributed via a guessed branch.

Each dissolved chain spans from one snapped node (or real junction) to another; pass-through nodes along the way are absorbed regardless of any attribute change there. Every model link attribute column (besides A, B, geometry) rides along onto the dissolved output, taken from each chain’s first constituent link — this default is only provisional here; Part C replaces it with a nearest-centroid resolution for multi-constituent chains.

Unlike the old strict-pseudonode set, FT_2027/LN_2027 uniformity across a chain’s constituents is no longer guaranteed by construction — a chain can now legitimately walk through a real FT- or lane-transition node. invariant_cols=() reflects that: both columns go through the same disagreement check as everything else, and a disagreement is expected and informational (Part C’s nearest-centroid resolution is what actually decides which constituent’s attributes a given physical piece gets), not a bug.

4 Part B — Piece-to-Chain Match

Stage 2 guarantees every link_pieces.gpkg boundary is already a snap point, so matching a piece to the dissolved chain it belongs to no longer needs any graph search — it’s a direct coordinate lookup followed by a vectorized (A,B) join:

  1. Look up each piece’s A_piece/B_piece node id from its rounded start/end coordinate via coord_to_node (built in Part A’s node-loading section). A piece with an unsnapped endpoint (e.g. a network-boundary edge) simply gets a null on that side — that’s expected, not an error.
  2. merge1 matches pieces drawn in the same direction as a dissolved chain (A_piece,B_piece == A,B — “forward”). merge2 matches pieces drawn in the opposite direction (B_piece,A_piece == A,B — “reverse”). Both can legitimately match the same physical piece: a typical two-way street is coded as two separate model-link rows (one per direction), each dissolving to its own A,B chain, so one physical piece produces two output rows — one per direction. A one-way road (e.g. a freeway, already digitized as a separate line per direction) matches only one side, producing one row.

5 Part C — Nearest-Constituent Attribute Resolution

matched can legitimately contain more than one candidate chain for the same (piece_id, piece_direction) — not only because a chain’s own constituent_ab_pairs may span multiple original hops, but because gdf_dissolved itself can contain multiple distinct chains sharing the same (A,B): self-loop branches (different loop roads that both start and end at the same real node) and genuine parallel paths (a direct link and a separate multi-hop alternate between the same two snapped nodes) both produce this. Node ids alone can’t disambiguate either case — only geometry can. A single rule handles both: explode every candidate chain’s constituent hops, join each hop to gdf_links for its attributes and geometry, measure distance from the piece’s centroid to each hop, and keep the global nearest hop per (piece_id, piece_direction) group. This simultaneously selects the correct candidate chain and the correct constituent’s attributes within it — a single-constituent, single-candidate group has exactly one hop and trivially “wins” regardless of distance.

### Snapped Nodes

Stage 2 guarantees every `link_pieces.gpkg` boundary is already a snap point,
so Stage 3 needs *which* nodes are snapped (split points) versus not. For the
"not" side, `is_topo_passthrough` from `nodes_classified.gpkg`
(`NeighborCount==2`, regardless of FT, lane count, or link-class/designation
uniformity) is safe to silently walk through and absorb into a multi-hop
chain in Part A — a node with exactly two distinct neighbors has exactly one
way to continue through it, full stop, no matter what changes there on the
model side. An unsnapped node that fails even that (3+ neighbors — a real
junction) is *not* pass-through: `dissolve_pseudonodes`'s single-preferred-edge
walk has no reliable way to know which of several real branches continues the
correct chain, so treating every unsnapped node as pass-through (as an
earlier version of this notebook did) silently produced wrong-branch chains
at those nodes. Only 2-neighbor nodes are dissolved through; any 3+-neighbor
unsnapped node is left as a hard chain boundary, and pieces touching it
honestly fail to match rather than getting attributed from a guessed
direction.

This is deliberately broader than `is_pseudo` (which additionally requires
uniform FT and uniform lane count, because it also gates Stage 1 snapping
eligibility — a snap *target* needs that stricter guarantee). Stage 3 only
needs the topological guarantee: real FT-transition, lane-transition, and
link-class-transition nodes have no physical vertex of their own in the
UGRC/UDOT centerlines (arcpy only cuts at genuine junctions), so treating
them as hard chain boundaries here — while `is_pseudo` correctly still sends
them to snapping in `01_node_classification.qmd` — was silently splitting one
physical piece across a model chain boundary the physical network was never

## Part A — Pass-Through Chain Dissolve

Collapse chains of model links connected through **pass-through nodes** —
the topological pass-through set (`pass_through_ids = pseudo_ids -
snapped_node_ids`; the subtraction is defensive, these nodes are never
snapped by design — see `01_node_classification.qmd`'s `is_topo_passthrough`).
A node only qualifies if it has exactly two distinct neighbors
(`NeighborCount==2`) — that alone is the guarantee the walk needs to be safe:
at a 2-neighbor node there is exactly one way to continue the chain, so
`dissolve_pseudonodes`'s preferred-else-first-found edge choice can't pick
wrong, regardless of whether FT, lane count, or link class (freeway/ramp/
surface designation) changes there. Only a real 3+-way junction — where
topology alone can't say which branch continues the same physical road — is
**not** pass-through here: it's a hard chain boundary, same as a snapped
node. Pieces whose real physical boundary sits at such a junction will fail
to match (`endpoints_only`/`a_only`/`b_only`) rather than silently being
attributed via a guessed branch.

Each dissolved chain spans from one snapped node (or real junction) to
another; pass-through nodes along the way are absorbed regardless of any
attribute change there. Every model link attribute column (besides `A`, `B`,
geometry) rides along onto the dissolved output, taken from each chain's
first constituent link — this default is only provisional here; Part C
replaces it with a nearest-centroid resolution for multi-constituent chains.

Unlike the old strict-pseudonode set, `FT_2027`/`LN_2027` uniformity across a
chain's constituents is **no longer** guaranteed by construction — a chain
can now legitimately walk through a real FT- or lane-transition node.
`invariant_cols=()` reflects that: both columns go through the same
disagreement check as everything else, and a disagreement is expected and
informational (Part C's nearest-centroid resolution is what actually decides
which constituent's attributes a given physical piece gets), not a bug.

## Part B — Piece-to-Chain Match

Stage 2 guarantees every `link_pieces.gpkg` boundary is already a snap point,
so matching a piece to the dissolved chain it belongs to no longer needs any
graph search — it's a direct coordinate lookup followed by a vectorized
`(A,B)` join:

1. Look up each piece's `A_piece`/`B_piece` node id from its rounded start/end
   coordinate via `coord_to_node` (built in Part A's node-loading section).
   A piece with an unsnapped endpoint (e.g. a network-boundary edge) simply
   gets a null on that side — that's expected, not an error.
2. `merge1` matches pieces drawn in the *same* direction as a dissolved chain
   (`A_piece,B_piece == A,B` — "forward"). `merge2` matches pieces drawn in
   the *opposite* direction (`B_piece,A_piece == A,B` — "reverse"). Both can
   legitimately match the same physical piece: a typical two-way street is
   coded as two separate model-link rows (one per direction), each dissolving
   to its own `A,B` chain, so one physical piece produces **two** output rows
   — one per direction. A one-way road (e.g. a freeway, already digitized as
   a separate line per direction) matches only one side, producing one row.

```{python}
gdf_pieces["A_piece"] = pd.Series(

gdf_pieces["B_piece"] = pd.Series(
```

## Part C — Nearest-Constituent Attribute Resolution

`matched` can legitimately contain more than one candidate chain for the same
`(piece_id, piece_direction)` — not only because a chain's own
`constituent_ab_pairs` may span multiple original hops, but because
`gdf_dissolved` itself can contain multiple distinct chains sharing the same
`(A,B)`: self-loop branches (different loop roads that both start and end at
the same real node) and genuine parallel paths (a direct link and a separate
multi-hop alternate between the same two snapped nodes) both produce this.
Node ids alone can't disambiguate either case — only geometry can. A single
rule handles both: explode every candidate chain's constituent hops, join
each hop to `gdf_links` for its attributes and geometry, measure distance
from the piece's centroid to each hop, and keep the global nearest hop per
`(piece_id, piece_direction)` group. This simultaneously selects the correct
candidate chain *and* the correct constituent's attributes within it — a
single-constituent, single-candidate group has exactly one hop and trivially
"wins" regardless of distance.

```{python}
matched = matched.reset_index(drop=True)
matched["match_id"] = matched.index
matched["_pairs"] = matched["constituent_ab_pairs"].apply(json.loads)
matched["_piece_centroid"] = matched.geometry.centroid

exploded = matched[["match_id", "piece_id", "piece_direction", "_pairs"]].explode(
    "_pairs", ignore_index=True
)
exploded["hop_A"] = exploded["_pairs"].str[0].astype("int64")
exploded["hop_B"] = exploded["_pairs"].str[1].astype("int64")
exploded = exploded.drop(columns="_pairs")

# Safe as an exact-key join: gdf_links has zero duplicate directed (A,B) pairs.
gdf_links_idx = gdf_links.set_index(["A", "B"])
exploded = exploded.join(gdf_links_idx, on=["hop_A", "hop_B"])

centroid_lookup = matched.set_index("match_id")["_piece_centroid"]
exploded["piece_centroid"] = exploded["match_id"].map(centroid_lookup)

exploded["dist_to_centroid"] = shapely.distance(
    exploded["geometry"].to_numpy(), exploded["piece_centroid"].to_numpy()
)

print(
    f"Exploded constituent-hop candidates: {len(exploded):,} "
    f"(from {matched['match_id'].nunique():,} matched chain rows, "
    f"{matched[['piece_id','piece_direction']].drop_duplicates().shape[0]:,} distinct piece/direction groups)"
)
```

corresponding model-link chain) keep exactly one row with blank attribute

geometry is ever generated** — this was the old BFS mechanism's failure mode
and the entire reason for this rewrite.
