GTFS Rail Shapes

Physical track geometry, one canonical shape per route (not per shape_id). A GTFS route typically publishes several shape_id variants — one per direction plus express/short-turn patterns — that all retrace the same physical track independently, each with its own slightly different GPS digitization. Naively dissolving every variant together (unary_union + linemerge, the same approach that works cleanly for CandidateTDMRoadLinks in 02_create_link.qmd) was tested directly against this feed and fails badly here: GEOS nodes the output at every point where two near-duplicate traces diverge by even a few centimetres, and — worse — a single shape can be non-simple on its own (self-crossing GPS noise), which explodes it into fragments all by itself. Confirmed directly: dissolving FrontRunner’s 7 raw shape variants together produced 297 chains (mean length 528 m) instead of one clean ~130 km corridor; even its single longest shape alone is non-simple and explodes into 5 pieces under unary_union.

Forward and backward service run the same physical track, so a single direction’s shape is a complete representation of a route’s alignment — there is no need to reconcile multiple variants at all. For each route, we keep only its longest shape (the fullest end-to-end trace) and use it as-is, self-intersections and all: split_candidate_links in 02_create_link.qmd cuts by M-value projection, which works correctly on a non-simple line, so the self-crossing noise is harmless as long as we never ask GEOS to topologically re-node it. Different routes that genuinely share physical trackage (e.g. TRAX Blue/Red through downtown) end up as separate, near-duplicate overlapping pieces after splitting — by design, the same pattern already used everywhere else in this pipeline for a two-way street digitized as two directional rows.

3 Part A — Origin Processing (Network Nodes)

A1 — Functional Type Flags

nodes_on(gdf_nodes, gdf_links, ft_codes) returns True for any node whose N appears as endpoint A or B of at least one link whose FT code is in ft_codes.

Flags are non-exclusive — a node touching both a freeway and a ramp link will be True for both Freeway and Ramp. Mutual exclusion is enforced later in the topology cascade (§A3).

A2 — Link Count, Neighbor Count, and Direction

count_links adds LinkCount — raw endpoint references per node, used for the distribution chart and diagnostics.

count_neighbors adds NeighborCount — the number of distinct neighboring nodes. This is the topologically correct pseudonode test: LinkCount breaks on bidirectional roads stored as two directional records (a pseudonode appears 4 times → LinkCount=4, not 2), while NeighborCount is always 2 for a true shape vertex regardless of storage convention.

A node is an is_pseudo shape vertex if and only if all three conditions hold: 1. NeighborCount == 2 — lies on a single path between two real junctions. 2. LinkFTCount == 1 — all connected links share the same exact FT code. A node where FT changes (e.g. FT 32→33) has a real physical endpoint in the centerline data and must be sent to snapping. 3. LinkLNCount == 1 — all connected links carry the same lane count. A lane-drop or lane-add node must not be dissolved away, as doing so would erase a model attribute boundary that affects TDM impedance.

assign_node_directions produces two direction columns (see docstring): - link_directions — freeway-priority cascade; used in passes (a) and (c). - fw_directions — freeway links only, majority-vote; used in pass (b) gore nodes.

_link_class[RAMP_LINK_MASK] = "ramp"

# For each node, count how many distinct link classes touch it.
_stacked_class = pd.concat([
    gdf_links[["A"]].assign(cls=_link_class.values).rename(columns={"A": "N"}),
    gdf_links[["B"]].assign(cls=_link_class.values).rename(columns={"B": "N"}),
], ignore_index=True)
_class_counts = _stacked_class.groupby("N")["cls"].nunique()
gdf_nodes["LinkClassCount"] = gdf_nodes["N"].map(_class_counts).fillna(0).astype(int)

# Count distinct FT codes per node.
# Stricter than LinkClassCount: nodes where FT changes (e.g. FT=32→33) register
# LinkFTCount=2 even though both belong to the freeway class.  Used in the
# link true-shape dissolution step to preserve model link boundaries where posted
# speed or facility sub-type changes — dissolving those nodes would corrupt TDM impedance.
_stacked_ft = pd.concat([
    gdf_links[["A", FT_COL]].rename(columns={"A": "N"}),
    gdf_links[["B", FT_COL]].rename(columns={"B": "N"}),
], ignore_index=True)
_ft_counts = _stacked_ft.groupby("N")[FT_COL].nunique()
gdf_nodes["LinkFTCount"] = gdf_nodes["N"].map(_ft_counts).fillna(0).astype(int)

# Count distinct lane counts per node — lane-drop/lane-add nodes must be snapped
# even when FT is uniform, because dissolving them would erase the lane change.
_stacked_ln = pd.concat([
    gdf_links[["A", "LN_2027"]].rename(columns={"A": "N"}),
    gdf_links[["B", "LN_2027"]].rename(columns={"B": "N"}),
], ignore_index=True)
_ln_counts = _stacked_ln.groupby("N")["LN_2027"].nunique()
gdf_nodes["LinkLNCount"] = gdf_nodes["N"].map(_ln_counts).fillna(0).astype(int)

# Pseudonode: shape vertex on a single homogeneous path — no physical snap target.
# Requires uniform FT AND uniform lane count: a lane-drop node has a real physical
# endpoint in the centerline data and must not be dissolved away. is_pseudo gates
# Part A3's node_type assignment below (a pseudonode gets no node_type / is never
# sent to spatial snapping) and must stay this strict — a snapping target still
# needs FT/LN uniformity to be a safe physical match.
gdf_nodes["is_pseudo"] = (
    (gdf_nodes["NeighborCount"] == 2)
    & (gdf_nodes["LinkFTCount"] == 1)
    & (gdf_nodes["LinkLNCount"] == 1)
)

# Broader topological pass-through flag, for Stage 3 chain dissolution only
# (03_transfer_attributes.qmd) — NOT used for snapping eligibility here.
# NeighborCount==2 alone is a sufficient safety guarantee on its own: a node
# with exactly two distinct neighbors has exactly one way to walk through it,
# regardless of whether FT, lane count, or link class (freeway/ramp/surface
# designation) changes there. Dropping the uniform-FT/uniform-LN/uniform-class
# requirements here (unlike is_pseudo above) lets Stage 3 dissolve through
# real FT/lane-transition and class-transition nodes that have no physical
# vertex of their own — the dominant cause of `endpoints_only` pieces, see
# _plan/freeway-endpoint-pool-diagnosis.md and the node-30208 (Antelope Island
# Causeway) example that first surfaced it. A node with 3+ neighbors is never
# included regardless — with a real branch, topology alone can't tell you
# which branch continues the same physical road (see dissolve_pseudonodes'
# docstring), so it must stay a hard boundary.
gdf_nodes["is_topo_passthrough"] = gdf_nodes["NeighborCount"] == 2

B2 — Classify Segments

Three mutually exclusive boolean flags per segment. Primary authority is DOT_FCLASS for freeway identification; DOT_RTNAME (UDOT LRS) supplements with explicit route numbers and ramp/CD facility characters. ONEWAY in (1, 2) elevates divided Principal Arterials into the freeway class (domain CVDomain_OneWay: 0=Two-way, 1=One-way direction of arc, 2=One-way opposite direction of arc).

DOT_RTNAME layout (11 characters, zero-padded):
  [0:4]  Route number      e.g. "0015" = I-15, "0154" = Bangerter
  [4]    LRS direction     "P" = primary (NB/EB),  "N" = negative (SB/WB)
  [5]    Facility type     " " = mainline, "R" = ramp, "C" = collector-distributor
  [6:]   Sequence/suffix   varies

These flags flow into every endpoint pool and type-tier decision, making this the primary place to audit when snapping results look wrong.

Hierarchical execution — first-call-wins. Nodes snapped in an earlier pass are skipped by subsequent passes.

D1 — Freeway and Interchange Snapping

Four passes in topology-priority order: (a) pure freeway, (a2) at-grade freeway crossings, (b) gore/gore_sf, (c) mid-ramp. All include fwy_sf in the D1 debug export so at-grade crossing snaps can be verified before running surface snapping.

Show the code 
# ── Endpoint pools ────────────────────────────────────────────────────────
#
# Each pool is now built from node_utils.allowed_ep_types(), which reads
# straight off _TYPE_TIER — the same table _spatial_snap uses to score
# candidates — instead of a hand-typed ep_type list. Diagnosis (2026-07-16)
# found the previous hand-typed pools had silently drifted narrower than
# _TYPE_TIER (and this section's own comments) already declared permitted:
# e.g. ("fwy", "gore"): 1 was documented as a Tier-1 fallback, but "gore"
# endpoints were never actually in the fwy pool below, so that fallback was
# dead code. Freeway/interchange node types took the brunt of it: their
# nearest real physical vertex is disproportionately a Tier-1 type one class
# over (arcpy only cuts centerlines at interchanges, not at the FT/lane
# -transition points that generate many freeway model nodes), and that
# vertex was almost always well within the search radius — median 100-150m
# vs. a 500m threshold — it just never reached the candidate pool. See
# node_utils.allowed_ep_types docstring for the full writeup. Any deviation
# from the raw tier table below is a deliberate, separately-justified
# business rule, called out inline.

# Pass (a) — fwy nodes → {fwy, gore, fwy_sf} (_TYPE_TIER tier ≤ 1 for "fwy").
#   ramp/surface are absent from _TYPE_TIER's "fwy" row entirely (not merely
#   tier>1), so they stay excluded — the divided-highway-collapse protection
#   this pool was designed for is unchanged, only the gore/fwy_sf Tier-1
#   fallback (previously dead) is now reachable.
ep_fwy_only = gdf_ep_unique[gdf_ep_unique["ep_type"].isin(allowed_ep_types("fwy"))].copy()

# Pass (a2) — fwy_sf nodes → _TYPE_TIER gives {fwy_sf, fwy, surface, gore};
#   surface is deliberately dropped here — if no fwy-class endpoint is within
#   range the node falls through to D2 (surface pass) where surface endpoints
#   are available under D2's own (more appropriate) direction logic.
ep_fwy_sf = gdf_ep_unique[
    gdf_ep_unique["ep_type"].isin(allowed_ep_types("fwy_sf") - {"surface"})
].copy()

#   type's _TYPE_TIER-allowed set is {fwy, fwy_sf, gore, ramp, ramp_sf}.
#   "fwy" is further restricted to multi-route hub interchanges
#   (fw_route_count >= 2) — a deliberate heuristic beyond what _TYPE_TIER
#   encodes, kept to avoid over-matching a gore node to an isolated

CC Attachment Nodes

Centroid connector attachment nodes are the network-side endpoints of FT_2027 = 1 (centroid connector) links — the taps where zone centroids connect to the road network. Zone centroids themselves (N < 3600) are excluded; only the network attachment nodes (N ≥ 3600) are retained.

These nodes are snapped to the nearest point on the nearest physical centerline (perpendicular projection, not nearest vertex or endpoint) using a simple STRtree lookup — no direction filtering, no greedy assignment. Centroid connectors essentially never attach to freeway mainline (checked directly: 23 of several thousand real-road links touching a CC attachment node are FT 31/33/35, the mainline codes), so the undirected divided-highway collision risk that rules out this approach for road-node snapping doesn’t apply here. The result is written as a second layer in nodes_snapped.gpkg.

A CC attachment node sometimes already coincides with a real junction that the direction-aware greedy snapper above already placed — already_snapped flags those directly against this notebook’s own gdf_nodes_snapped output (the snapped column), not inferred from anything else. use_as_split = snap_resolved & ~already_snapped is the one column Stage 2/3 actually consume: reusing an already-snapped node’s independently-computed nearest- point coordinate here would plant a second, slightly different split a few cm away from the real one, producing a sliver instead of a clean cut. Unresolved nodes (> 100 m) are simply excluded — same as any other unsnapped node, no special handling.

External station nodes (EXTERNAL_ = 1 on the node table, N 3601–3629) are gateway points where the model network intentionally truncates at the edge of the modelled region — canyon passes, state lines (e.g. “I-15 to Tremonton”, “SR 190 Guardsman Pass”). Re-flagging Mid-Link Attachment Nodes as Hard Boundaries

NeighborCount (Part A, top of this notebook) is computed from the FT_2027-filtered link table, so a CC node’s FT=1 spur is invisible to it. When the model inserts a CC/external attachment node strictly between two intersections — coding the through road as two separate link rows, intersection1 → node and node → intersection2 — that node sees only its two real-road neighbors and looks like an ordinary shape point: is_topo_passthrough = True. 03_transfer_attributes.qmd’s pass-through dissolve then silently walks through it, merging both halves into one chain with no split at the node’s true location and no separate attribute transfer for either half. use_as_split (computed above) is exactly the set of nodes where this applies: resolved, and not already snapped/handled elsewhere. A node already at a real junction already has is_topo_passthrough = False and needs no change.

Rail station nodes just snapped in D3 have the exact same failure mode — a mid-line station (e.g. an intermediate TRAX stop with no other junction) sees only its two rail neighbors and looks like an ordinary pass-through point, but it’s now a genuine split point for the rail pieces built in 02_create_link.qmd’s Part F — so it’s folded into the same patch below.

### GTFS Rail Shapes

Physical track geometry, one canonical shape per route (not per `shape_id`).
A GTFS route typically publishes several `shape_id` variants — one per
direction plus express/short-turn patterns — that all retrace the *same*
physical track independently, each with its own slightly different GPS
digitization. Naively dissolving every variant together (`unary_union` +
`linemerge`, the same approach that works cleanly for `CandidateTDMRoadLinks`
in `02_create_link.qmd`) was tested directly against this feed and fails
badly here: GEOS nodes the output at every point where two near-duplicate
traces diverge by even a few centimetres, and — worse — a single shape can
be non-`simple` on its own (self-crossing GPS noise), which explodes it into
fragments all by itself. Confirmed directly: dissolving FrontRunner's 7 raw
shape variants together produced 297 chains (mean length 528 m) instead of
one clean ~130 km corridor; even its single longest shape alone is
non-simple and explodes into 5 pieces under `unary_union`.

Forward and backward service run the *same* physical track, so a single
direction's shape is a complete representation of a route's alignment —
there is no need to reconcile multiple variants at all. For each route, we
keep only its longest shape (the fullest end-to-end trace) and use it
as-is, self-intersections and all: `split_candidate_links` in
`02_create_link.qmd` cuts by M-value projection, which works correctly
on a non-simple line, so the self-crossing noise is harmless as long as we
never ask GEOS to topologically re-node it. Different routes that
genuinely share physical trackage (e.g. TRAX Blue/Red through downtown)
end up as separate, near-duplicate overlapping pieces after splitting —
by design, the same pattern already used everywhere else in this pipeline
for a two-way street digitized as two directional rows.

```{python}
trip_shape_route = (
```

### A1 — Functional Type Flags

`nodes_on(gdf_nodes, gdf_links, ft_codes)` returns True for any node whose
N appears as endpoint A or B of at least one link whose FT code is in `ft_codes`.

Flags are **non-exclusive** — a node touching both a freeway and a ramp link
will be True for both `Freeway` and `Ramp`. Mutual exclusion is enforced later
in the topology cascade (§A3).


### A2 — Link Count, Neighbor Count, and Direction

`count_links` adds `LinkCount` — raw endpoint references per node, used for the
distribution chart and diagnostics.

`count_neighbors` adds `NeighborCount` — the number of **distinct** neighboring
nodes. This is the topologically correct pseudonode test: `LinkCount` breaks on
bidirectional roads stored as two directional records (a pseudonode appears 4
times → LinkCount=4, not 2), while NeighborCount is always 2 for a true shape
vertex regardless of storage convention.

A node is an `is_pseudo` shape vertex if and only if all three conditions hold:
1. **NeighborCount == 2** — lies on a single path between two real junctions.
2. **LinkFTCount == 1** — all connected links share the same exact FT code.
   A node where FT changes (e.g. FT 32→33) has a real physical endpoint in the
   centerline data and must be sent to snapping.
3. **LinkLNCount == 1** — all connected links carry the same lane count.
   A lane-drop or lane-add node must not be dissolved away, as doing so would
   erase a model attribute boundary that affects TDM impedance.

`assign_node_directions` produces two direction columns (see docstring):
- `link_directions` — freeway-priority cascade; used in passes (a) and (c).
- `fw_directions`   — freeway links only, majority-vote; used in pass (b) gore nodes.

```{python}
gdf_nodes = count_links(gdf_nodes, gdf_links)
gdf_nodes = count_neighbors(gdf_nodes, gdf_links)
gdf_nodes = assign_node_directions(gdf_nodes, gdf_links, freeway_ft_codes=FW_CODES)

# Assign one class label per link using the already-defined mutually exclusive masks.
_link_class = pd.Series("other", index=gdf_links.index)
_link_class[FWY_LINK_MASK]  = "freeway"
_link_class[RAMP_LINK_MASK] = "ramp"
_link_class[SURFACE_LINK_MASK] = "surface"
_link_class[gdf_links[FT_COL].isin({70, 80})] = "transit"

# For each node, count how many distinct link classes touch it.
_stacked_class = pd.concat([
    gdf_links[["A"]].assign(cls=_link_class.values).rename(columns={"A": "N"}),
    gdf_links[["B"]].assign(cls=_link_class.values).rename(columns={"B": "N"}),
], ignore_index=True)
_class_counts = _stacked_class.groupby("N")["cls"].nunique()
gdf_nodes["LinkClassCount"] = gdf_nodes["N"].map(_class_counts).fillna(0).astype(int)

# Count distinct FT codes per node.
# Stricter than LinkClassCount: nodes where FT changes (e.g. FT=32→33) register
# LinkFTCount=2 even though both belong to the freeway class.  Used in the
# link true-shape dissolution step to preserve model link boundaries where posted
# speed or facility sub-type changes — dissolving those nodes would corrupt TDM impedance.
_stacked_ft = pd.concat([
    gdf_links[["A", FT_COL]].rename(columns={"A": "N"}),
    gdf_links[["B", FT_COL]].rename(columns={"B": "N"}),
], ignore_index=True)
_ft_counts = _stacked_ft.groupby("N")[FT_COL].nunique()
gdf_nodes["LinkFTCount"] = gdf_nodes["N"].map(_ft_counts).fillna(0).astype(int)

# Count distinct lane counts per node — lane-drop/lane-add nodes must be snapped
# even when FT is uniform, because dissolving them would erase the lane change.
_stacked_ln = pd.concat([
    gdf_links[["A", "LN_2027"]].rename(columns={"A": "N"}),
    gdf_links[["B", "LN_2027"]].rename(columns={"B": "N"}),
], ignore_index=True)
_ln_counts = _stacked_ln.groupby("N")["LN_2027"].nunique()
gdf_nodes["LinkLNCount"] = gdf_nodes["N"].map(_ln_counts).fillna(0).astype(int)

# Pseudonode: shape vertex on a single homogeneous path — no physical snap target.
# Requires uniform FT AND uniform lane count: a lane-drop node has a real physical
# endpoint in the centerline data and must not be dissolved away. is_pseudo gates
# Part A3's node_type assignment below (a pseudonode gets no node_type / is never
# sent to spatial snapping) and must stay this strict — a snapping target still
# needs FT/LN uniformity to be a safe physical match.
gdf_nodes["is_pseudo"] = (
    (gdf_nodes["NeighborCount"] == 2)
    & (gdf_nodes["LinkFTCount"] == 1)
    & (gdf_nodes["LinkLNCount"] == 1)
)

# Broader topological pass-through flag, for Stage 3 chain dissolution only
# (03_transfer_attributes.qmd) — NOT used for snapping eligibility here.
# NeighborCount==2 alone is a sufficient safety guarantee on its own: a node
# with exactly two distinct neighbors has exactly one way to walk through it,
# regardless of whether FT, lane count, or link class (freeway/ramp/surface
# designation) changes there. Dropping the uniform-FT/uniform-LN/uniform-class
# requirements here (unlike is_pseudo above) lets Stage 3 dissolve through
# real FT/lane-transition and class-transition nodes that have no physical
# vertex of their own — the dominant cause of `endpoints_only` pieces, see
# _plan/freeway-endpoint-pool-diagnosis.md and the node-30208 (Antelope Island
# Causeway) example that first surfaced it. A node with 3+ neighbors is never
# included regardless — with a real branch, topology alone can't tell you
# which branch continues the same physical road (see dissolve_pseudonodes'
# docstring), so it must stay a hard boundary.
gdf_nodes["is_topo_passthrough"] = gdf_nodes["NeighborCount"] == 2

print(f"Pseudonodes (NeighborCount==2, uniform FT+LN): {gdf_nodes['is_pseudo'].sum():,}")
print(f"  of which LinkCount==2: {(gdf_nodes['is_pseudo'] & (gdf_nodes['LinkCount'] == 2)).sum():,}")
print(f"  of which LinkCount> 2: {(gdf_nodes['is_pseudo'] & (gdf_nodes['LinkCount'] > 2)).sum():,}  ← bidirectional road pseudonodes")
print(f"Class-transition nodes (NeighborCount==2, multi-class): {((gdf_nodes['NeighborCount'] == 2) & (gdf_nodes['LinkClassCount'] > 1)).sum():,}  ← real junctions, must be snapped")
print(f"FT-transition nodes sent to snapping (NeighborCount==2, same class, diff FT): {((gdf_nodes['NeighborCount'] == 2) & (gdf_nodes['LinkClassCount'] == 1) & (gdf_nodes['LinkFTCount'] > 1)).sum():,}")
print(f"LN-transition nodes sent to snapping (NeighborCount==2, uniform FT, diff LN): {((gdf_nodes['NeighborCount'] == 2) & (gdf_nodes['LinkFTCount'] == 1) & (gdf_nodes['LinkLNCount'] > 1)).sum():,}")
print(f"is_topo_passthrough (NeighborCount==2, any FT/LN/class): {gdf_nodes['is_topo_passthrough'].sum():,}  ← Stage 3 dissolve set (broader than is_pseudo by {gdf_nodes['is_topo_passthrough'].sum() - gdf_nodes['is_pseudo'].sum():,})")
```

### A3 — Node Topology Classification

Eight mutually-exclusive `node_type` labels. Transit is evaluated first and
takes priority over all road-class combinations. The remaining seven labels

```{python}
no_pseudo = ~gdf_nodes["is_pseudo"]
```

### B2 — Classify Segments

Three mutually exclusive boolean flags per segment. Primary authority is
`DOT_FCLASS` for freeway identification; `DOT_RTNAME` (UDOT LRS) supplements with
explicit route numbers and ramp/CD facility characters. `ONEWAY` in (`1`, `2`)
elevates divided Principal Arterials into the freeway class (domain CVDomain_OneWay:
0=Two-way, 1=One-way direction of arc, 2=One-way opposite direction of arc).

```
DOT_RTNAME layout (11 characters, zero-padded):
  [0:4]  Route number      e.g. "0015" = I-15, "0154" = Bangerter
  [4]    LRS direction     "P" = primary (NB/EB),  "N" = negative (SB/WB)
  [5]    Facility type     " " = mainline, "R" = ramp, "C" = collector-distributor
  [6:]   Sequence/suffix   varies
```

These flags flow into every endpoint pool and type-tier decision, making this
the **primary place to audit** when snapping results look wrong.


### B4 — Deduplicate by Tolerance-Based Clustering

Cluster raw endpoints by true single-linkage distance (`cluster_endpoints`,
`ENDPOINT_CLUSTER_TOLERANCE_M` = 1cm) rather than a rounded-coordinate grid
bucket — two points 2mm apart that happen to round into different 1cm grid
cells (e.g. `10.004999` → `10.00` vs `10.005001` → `10.01`) are now correctly
merged. Aggregate type flags with OR — a cluster is `is_freeway=True` if any
freeway segment terminates there. The output geometry keeps the exact
(unrounded) coordinate of one contributing raw endpoint rather than
reconstructing a point from the rounded key, so `gdf_ep_unique` — and every
node later snapped onto it — stays bit-exact with a real `CandidateTDMRoadLinks`
vertex instead of sitting on a 1cm quantization grid. `x_round`/`y_round` are
still carried through (first raw point) for QGIS inspection and for
`link_utils.resolve_snap_coords`'s downstream nearest-vertex lookup, which
is out of scope for this change.

### D3 — Transit Snapping

FixedTransit nodes snap to Light Rail (TRAX) and Commuter Rail (FrontRunner)

### CC Attachment Nodes

Centroid connector attachment nodes are the network-side endpoints of FT_2027 = 1
(centroid connector) links — the taps where zone centroids connect to the road
network. Zone centroids themselves (N < 3600) are excluded; only the network
attachment nodes (N ≥ 3600) are retained.

These nodes are snapped to the nearest **point** on the nearest physical
centerline (perpendicular projection, not nearest vertex or endpoint) using a
simple STRtree lookup — no direction filtering, no greedy assignment.
Centroid connectors essentially never attach to freeway mainline (checked
directly: 23 of several thousand real-road links touching a CC attachment
node are FT 31/33/35, the mainline codes), so the undirected divided-highway
collision risk that rules out this approach for road-node snapping doesn't
apply here. The result is written as a second layer in `nodes_snapped.gpkg`.

A CC attachment node sometimes already coincides with a real junction that
the direction-aware greedy snapper above already placed — `already_snapped`
flags those directly against this notebook's own `gdf_nodes_snapped` output
(the `snapped` column), not inferred from anything else. `use_as_split =
snap_resolved & ~already_snapped` is the one column Stage 2/3 actually
consume: reusing an already-snapped node's independently-computed nearest-
point coordinate here would plant a second, slightly different split a few
cm away from the real one, producing a sliver instead of a clean cut.
Unresolved nodes (> 100 m) are simply excluded — same as any other unsnapped
node, no special handling.

### Re-flagging Mid-Link Attachment Nodes as Hard Boundaries

`NeighborCount` (Part A, top of this notebook) is computed from the
FT_2027-filtered link table, so a CC node's FT=1 spur is invisible to it. When
the model inserts a CC/external attachment node strictly between two
intersections — coding the through road as two separate link rows,
`intersection1 → node` and `node → intersection2` — that node sees only its
two real-road neighbors and looks like an ordinary shape point:
`is_topo_passthrough = True`. `03_transfer_attributes.qmd`'s pass-through
dissolve then silently walks through it, merging both halves into one chain
with no split at the node's true location and no separate attribute transfer
for either half. `use_as_split` (computed above) is exactly the set of nodes
where this applies: resolved, and not already snapped/handled elsewhere. A
node already at a real junction already has `is_topo_passthrough = False` and
needs no change.

Rail station nodes just snapped in D3 have the exact same failure mode —
a mid-line station (e.g. an intermediate TRAX stop with no other junction)
sees only its two rail neighbors and looks like an ordinary pass-through
point, but it's now a genuine split point for the rail pieces built in
`02_create_link.qmd`'s Part F — so it's folded into the same patch below.

```{python}
rail_snapped_ids = set(
    gdf_nodes_snapped.loc[
        gdf_nodes_snapped["snapped"].fillna(False) & (gdf_nodes_snapped["snap_rule"] == "FixedTransit_Rail"),
        "N",
    ]
)
attach_ids = (
    set(gdf_cc_snapped.loc[gdf_cc_snapped["use_as_split"], "N"])
    | set(gdf_ext_snapped.loc[gdf_ext_snapped["use_as_split"], "N"])
    | rail_snapped_ids
)

was_mid_link_passthrough = gdf_nodes["N"].isin(attach_ids) & gdf_nodes["is_topo_passthrough"]
n_patched = int(was_mid_link_passthrough.sum())
gdf_nodes.loc[was_mid_link_passthrough, "is_topo_passthrough"] = False

gdf_nodes.to_crs(CRS_UTM).to_file(PATHS["out_node_classified"], driver="GPKG")
print(
    f"Patched is_topo_passthrough=False for {n_patched:,} mid-link CC/external/rail "
    f"attachment node(s) (of {len(attach_ids):,} new split points total — the "
    f"rest already sat at a real junction and needed no change)."
)
print(f"Re-exported {PATHS['out_node_classified']} with the patch.")
```
